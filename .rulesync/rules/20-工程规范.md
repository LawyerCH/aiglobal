# 工程规范

> 借鉴 Google eng-practices（small CLs）与 Conventional Commits。

## 提交规范（Conventional Commits）
- 格式：`<type>(<scope>): <描述>`
- `type`：`feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert`
- 描述用祈使句，一行说清「做了什么、为什么」
- 破坏性变更在 footer 标注 `BREAKING CHANGE:`

## 小步提交（Small CLs）
- 每次改动尽量**小、自包含**，只解决**一件事**（一个功能的一部分，而非整个功能）
- 相关测试与代码放**同一次**提交
- 重构与功能/修复**分开**提交（大规模移动/重命名尤其如此）
- 宁可偏小；大改动先拆成一系列小改动
- 不破坏构建：依赖链上每次提交后，系统都应可用

## 代码卫生
- 只改与任务相关的代码，**不顺手大范围重排格式**
- **不把密钥/凭据写进代码**，用环境变量或 `.env`（`.env` 必须进 `.gitignore`）
- 新增依赖前先确认无现成方案，并说明理由（呼应环境纪律：宁少勿多）
- 完成前自检：能跑通、无明显回归、改动范围符合预期
